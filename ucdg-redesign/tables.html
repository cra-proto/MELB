Tables

A table is for data that has to be compared across two dimensions — rows of items that each share the same set of columns. That is a narrow job. Most things put in tables are really lists or plain text, and they read better that way, especially on a phone. Reach for a table only when the reader genuinely needs to compare values across rows.

Choose the right pattern

Before you build a table, ask what the reader is doing with the information. A table earns its place only when they compare the same attributes across several items.

Table

Use when each item has the same two or more attributes the reader compares across rows — rates by year, amounts by category.

List

Use when items have one attribute, or the reader reads down rather than across — a set of documents, options, or steps.

Plain text

Use when there are only a few values, or the relationship is simple enough to say in a sentence or two.

Quick decision guide

  • Does the reader compare the same attributes across several items? → Table
  • Is it a set of items with one attribute each? → List
  • Are there only two or three values? → Plain text
  • Would the table need more than a couple of columns to make sense? → split it, or rethink whether it's a table at all

What to include

  • A caption that says what the table shows
  • Clear, concise column and row headers — the labels that let a reader (and a screen reader) locate a cell
  • The simplest structure that works — prefer two simple tables over one merged, multi-level table
  • Data aligned consistently: text left, numbers right so digits line up, headers matching their column's alignment
  • Columns and rows ordered by importance to the reader, not by how the data happened to arrive

Guidance

  • Consider alternatives first. If a "table" has one column of items, it's a list. If it's a couple of facts, it's a sentence.
  • Simplify structure. Avoid merged cells and stacked header rows. Break one complex table into two simple ones.
  • Align for scanning. Right-align numbers so place values line up; left-align text.
  • Order by importance. Put the column and rows the reader cares about most first.
  • Large tables: add a search filter and pagination so the reader can find and reorder rows.
  • Avoid blank cells. An empty cell is ambiguous — use "0", "Not applicable", or "—" with a consistent meaning.
  • Make it responsive. A table must reflow or scroll cleanly on a phone, not force the whole page sideways.

Accessibility

  • Use real table markup with a <caption> and proper <th> headers with scope, so screen readers can announce which row and column a cell belongs to.
  • Do not use a table for layout — only for genuine tabular data.
  • Keep the structure simple; complex merged headers are very hard to navigate with a screen reader.
  • Ensure the table reflows or scrolls within its own container at small sizes and high zoom, without breaking the page layout.
  • Don't rely on zebra striping alone to separate rows — it helps sighted users but must not be the only cue.

Examples

Compare tables side by side

Good table use
  • A tax-bracket table: rows are income ranges, columns are the rate and the tax owing — the reader compares the same attributes across rows. Numbers right-aligned, a clear caption.
  • A "payment dates" table with two columns — benefit and payment date — kept simple, with no merged cells.
  • A complex eligibility table is replaced by two simple tables, one per situation, each easy to read on a phone.
Tables to avoid
  • A single-column "table" listing accepted documents.
    Why it is wrong: one column is a list, not a table. Use a bulleted list.
  • A table with merged cells and two stacked header rows to fit every scenario.
    Why it is wrong: merged, multi-level headers are nearly impossible to navigate with a screen reader. Split into simple tables.
  • Numbers left-aligned so 9, 45, and 1,200 don't line up, with several blank cells.
    Why it is wrong: misaligned numbers are hard to compare, and blank cells are ambiguous. Right-align numbers; fill cells with a clear value.
  • A wide data table that forces the whole page to scroll sideways on a phone.
    Why it is wrong: it breaks the responsive layout. Let the table scroll inside its own container.
